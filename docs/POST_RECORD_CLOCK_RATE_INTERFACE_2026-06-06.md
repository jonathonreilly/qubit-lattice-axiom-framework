## Result

The exact post-record layer supplies an event-indexed append/count structure:

```text
word prefixes: empty, o_1, o_1 o_2, ..., o_1 ... o_n
event index:   0,     1,   2,         ..., n
count update:  c -> c + e_o
```

This gives order, prefix preservation, length, and finite count increments. It
does not supply physical elapsed time, a clock metric, transition rates, a
Hamiltonian, or a transfer step.

The clean interface is:

```text
post-record word/count stream
  + supplied clock map tau: {0,...,n} -> R with tau_0 < ... < tau_n
    => durations Delta tau_k = tau_{k+1} - tau_k
    => empirical event/count rates relative to tau.
```

Without the supplied `tau`, the same record history supports many inequivalent
rates.

## No-Go Claim

Finite post-record histories determine a discrete event order, not a physical
time metric. A finite history of length `n` can be embedded into physical time
by any strictly increasing finite clock sequence

```text
tau_0 < tau_1 < ... < tau_n.
```

All such choices preserve the same word, same counts, same prefix order, and
same finite additivity. They generally give different elapsed times and rates.

For example, the same four-event word can be assigned:

```text
tau_uniform   = (0, 1, 2, 3, 4)
tau_slow      = (0, 2, 4, 6, 8)
tau_accel     = (0, 1, 3, 6, 10)
```

The record word and counts are unchanged, but the total event rates are
`4/4`, `4/8`, and `4/10`. Therefore post-record append/count dynamics does not
determine a clock rate.

## What this does support

Once a clock map is supplied, the post-record count layer gives exact derived
quantities:

- total event rate `n / (tau_n - tau_0)`;
- per-letter empirical rates `count_o(w) / (tau_n - tau_0)`;
- interval rates `1 / (tau_{k+1} - tau_k)`;
- coarse-grained rates after an explicit alphabet map.

Those rates are conditional on the clock map. They are not generated by Record
alone.

## Dynamics implication

This isolates the time/rate residual in the dynamics program:

```text
pre-record carrier dynamics
  -> record-production process
  -> realized atom stream
  -> post-record event-indexed history/counts
  + clock/rate bridge
    => physical rates.
```

The exact post-record layer gives the event sequence a stable information
grammar. A physical dynamics claim that needs rates must still supply:

- a clock or time metric;
- a production process or stochastic kernel over events;
- a carrier Hamiltonian/transfer step if physical evolution is claimed.

## What this unlocks

- Rows that only need event order, prefix preservation, finite length, counts,
  or coarse-grained event counts can cite the exact post-record stack.
- Rows that report rates must identify the clock denominator and state whether
  it is event count, coordinate time, proper time, lattice step, transfer-step
  count, or an external observation window.
- Rows that claim physical dynamics cannot cite append/count algebra as a
  Hamiltonian, Markov kernel, or transition-rate derivation.

## Boundaries

- Does not deny that a supplied clock can define rates for a record stream.
- Does not deny that a supplied stochastic process can produce event times.
- Does not derive a clock, time metric, transition rate, Hamiltonian, action,
  transfer operator, or coupling.
- Does not derive probabilities or Born weights.
- Does not select a generation or Koide dial location.
- Does not apply any audit verdict.
